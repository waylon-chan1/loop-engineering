# Changelog

Engine changes only — what changed in the process, and what motivated it. Newest first.

Two rules keep this file honest and publishable: an entry names the rule that changed and the *class* of evidence behind it, never the private task that surfaced it; and repository-specific facts never appear here, because they belong in an adapter, which is not part of this repository.

## 2026-09-04

- **Review rounds track pushes, not defects — so fixes ship one push per round.** Measured across two repositories: the count of blocking bot reviews on a pull request correlates with the number of post-open pushes at r≈0.9 (~0.8 rounds per push), not with how many findings were valid. The mechanism is mechanical — every push re-arms every bot against a diff it has already read — so a batch fixed across many small pushes pays a round for each one, and a partial push made while the rest of the batch is still being adjudicated buys a full extra round for what was left behind. The largest observed case spent thirteen pushes on twenty-two accepted findings and drew nine rounds, four of which carried findings created by the previous round's own fix; a comparable change pushed once drew one. Review-loop now requires adjudicating the whole batch, fixing every accepted finding in it, then pushing once and re-requesting review. Evidence: confirmed in two repositories, sixteen pull requests measured.

## 2026-09-01

- **An edit is a claim, and "applied" is not the same as "landed".** A search-and-replace on a non-unique anchor hits the wrong occurrence; one whose target a formatter has reflowed matches nothing and no-ops. The tool reports success either way, so every check downstream then measures the unedited file — and a mutation check, a suite run, or a state transition can each come back apparently confirming work that was never applied. § Claims and evidence now requires re-reading the target and confirming the change is present before running anything that depends on it, and prefers anchors shown to be unique. Evidence: confirmed in two repositories — a status edit that silently rewrote a quoted line inside a frozen evidence record instead of the header it aimed at, falsifying that record while leaving the intended change undone; and a code edit that no-opped after a formatter reflow, after which a falsifiability check was re-run against the unchanged file and nearly reported an unguarded change as verified.

- **A stage owns its repository's working tree, and ownership cannot be inferred from silence.** Concurrency control here had only a fan-out cap, which bounds how many agents exist but not how many touch one tree. The gap is an inference: no durable artifact distinguishes a working agent from a wedged one, because state advances only at the *end* of a stage — so a completion notification, an unadvanced state, and a missing output section are each equally consistent with a successor still running. § Chaining now requires establishing that no other agent owns a tree before spawning into it or grading its diff, resolving ownership by asking rather than by inferring death from silence, and waiting rather than spawning when it cannot be established; a grading stage additionally records the commit it graded and re-derives if the tree moves. Evidence: one severe miss, recurring after a prior graduation that addressed the inference but not the control — three collisions in a single task, including two duplicate agents spawned in one action and a grading pass whose subject changed underneath it mid-run.

## 2026-08-30

- **A premise must be checked before it is classified, and before it is escalated.** Adjudication routes a review comment on its *Why*, and a Why almost always rests on a factual claim — what a vendor returns, what a config resolves to, what a call site passes. The routing table was sound; nothing required the claim feeding it to be true. So the class now has to be established by the cheapest means that actually settles it — read the code, grep the callers, call the sandbox — and the escalation class carries the highest bar, because an escalation built on an unchecked premise spends the approver's judgement while looking like diligence. A new hard rule forbids asserting any checkable fact that has not been checked, in a verdict, a reply, an escalation, or a justification offered for a decision. Evidence: confirmed in two repositories — claims published ahead of their evidence in one, and in the other a bot finding escalated as a frozen-criteria hole on an unverified vendor behaviour that a four-minute probe reduced to a dismissal, after the same unverified premise had already been used to propose a schema migration.

- **Probes go at the boundary the code owns.** A criterion of the form "X still works when Y fails" was certified as passing by three consecutive fresh-eyes verifications, each of which injected the failure by mutating the dependency's internals — proving only that the dependency handles its own errors. The real escape hatch sat in an initialisation check that ran *before* that error boundary, so the failure propagated in production code while every probe reported it contained. Verification now has to locate where a dependency's guarantees end, by reading its source, and inject at the caller's side of that line; the strongest form of such a probe needs no stubbing at all. Evidence: one severe miss — a stated criterion certified false three times, then found by an outside reviewer in a single pass.

## 2026-08-28

- **Added a check-don't-assume protocol binding every agent.** A load-bearing claim — one deciding a criterion, a design, a verdict, a deviation, a stop, or an escalation — must be *verified* (cite `file:line`), *probed* (cite the command and its output), or else it is *assumed*, and an assumed claim may not be load-bearing. It becomes a probe, an open question, or a criterion instead. Stops and escalations now state what was checked and what it showed, since an escalation resting on an assumption spends a human's attention on a question a one-minute probe would have closed. Nothing is built for a case whose path hasn't been demonstrated. Verified claims stay reusable until a rebase, dependency bump, vendor change, or companion deploy moves the ground, and effort scales with what the claim carries, so a variable name needs no ceremony while an architecture does. Consolidates rules that previously existed only inside the planning stage and bound none of the others.

- **Re-verification narrowed to the blast radius.** The first verification covers the whole contract; every round after it re-derives only what the change could have moved. Specs still run in full every round — one command, and it is what makes narrowing safe — while manual and user criteria are re-exercised only inside a radius computed from the diff against the build list's `Files:`/`Criteria:` lines, never from an agent's sense of what feels related. Everything outside keeps its verdict, marked as carried forward, and returns to the radius the moment a later diff touches its code. When the radius cannot be computed — no `Files:` lines, shared or global code, a config or dependency change — it is everything. Replaces a rule that re-adjudicated all criteria every round: correct, but it charged a full manual pass for a one-line repair.

- **Merge-ready became a checkable state, and the merge is now recorded.** A PR is merge-ready when the forge reports it mergeable — CI green, approval requirements met, no requested changes outstanding — and nothing is still escalated to a human. Merging is the human's in every repo and every tier; no skill may do it. Because nothing is running at the moment someone clicks merge, `in-review → merged` is settled by asking the forge afterwards: the PR url is recorded in the plan document's new `PR:` header, and retro's sweep resolves every document left in review before harvesting. Without that pass the lifecycle could reach a merged PR and never close, so no lesson would ever be harvested.

- **Review-loop hardened against reviewer persuasion.** Every comment reaches adjudication decomposed into What / Why / How — the Why is what gets classified, and the How is the author's to decide, with the reviewer's proposal weighed as input. AI reviewers are held to the format (the PR body states it; one format-demand reply before any adjudication effort); human reviewers are never forced into a form — the agent derives the structure and asks one targeted question only for what can't be derived. A verdict re-opens on new evidence only, never on restatement; insisted-on defects resolve by failing repro or not at all; a human's second round of disagreement is re-judged blind by a fresh adjudicator that sees the decomposed claim but not who is arguing or how insistently. Shipping a change the tally adjudicated invalid, absent new evidence or an approver override, is now a named severe miss (`caved-without-evidence`) — and the reverse failure, a dismissal later proven wrong, is tracked with equal weight, so the equilibrium is evidence, not defiance. Reviewer calibration may tune investigation effort, never verdicts.

- **The post-PR stage became a skill: review-loop.** It opens the PR, publishes the plan's reviewer-facing rendering, polls for comments, and adjudicates every one against the acceptance-criteria contract: a comment must indict compliance, indict the contract itself, or cite the repo's own rules — otherwise it gets an evidence-based pushback. Bots get one reply then a resolution; humans get at most two rounds of disagreement, then escalation — the loop never filibusters a colleague. Accepted comments are fixed as nested patch lifecycles (spec first, fresh verify), the tally feeds retro's attribution, and a private per-reviewer ledger (outside this repo) lets known preferences be pre-empted without ever trading quality for approval. New status `in-review` between `verified-local` and `merged`.

- **Split the engine from its memory.** Real adapters moved to a private store and are symlinked back in, so this repository can be public while carrying no repository facts at all. Added a README, an MIT license, an example adapter, and a whitelist `.gitignore` — `~/.claude/skills` is where every user-level skill lands, so a file now joins the public engine deliberately rather than by being in the directory.
- **Tiered work by complexity, not size.** `plan-loop` classifies every task as patch, feature, or deep at Stage 0. Patch collapses to one combined gate; deep requires alternatives and a failure-mode registry. A two-file race-condition fix is deep; a twenty-file mechanical rename is not.
- **Tests split into scaffolding and contract.** Tests are unlimited during build, but only those tracing to a criterion, a failure mode, a regression, or a boundary contract survive into the PR. Prompted by a first live run that shipped 2,241 test lines against roughly 830 source lines.
- **Added the CHANGED verdict.** A criterion satisfied by different means than the plan described, backed by a logged deviation, is now distinguishable from both a failure and a silent deviation. Verify is conservative with PASS and generous with CHANGED: the goal is what was promised, not the route.
- **Findings must quote their evidence.** A FAIL cites the failing command and its output, or file:line and verbatim text. A failure that cannot be quoted is a suspicion, and a suspicion may not trigger the repair loop.
- **Added the planning pushback kit.** Premise challenge, claimed-limitations-need-evidence, and a ban on non-committal phrasing — balanced by never re-arguing a decision the approver has already made.
- **Added decision briefs and the outside voice.** Anything surfaced at a gate carries stakes, a recommendation, and trade-offs, classified as mechanical, taste, or challenge. Feature and deep tiers additionally get a cold-read subagent whose only charter is to find how the plan fails.
- **Added the observations flight recorder.** Any agent may append a dated, factual line to the plan document the moment it hits friction. Facts live there; only retro turns them into rules, and only when independently confirmed.
- **Lessons bucket by class and promote by spread.** Adjacency is judged by a controlled vocabulary rather than wording, `Times Seen` counts distinct tasks rather than mentions, and a lesson confirmed in one repository may only reach that repository's adapter. Two repositories are required before anything may change the engine — which is what keeps the engine generic by construction rather than by discipline.

The tier rubric's structure, the pushback kit, decision briefs, the outside voice, the CHANGED verdict, the regression rule, and the scaffolding-vs-contract policy were scavenged from [gstack](https://github.com/garrytan/gstack).

## 2026-08-27 — first version

- **The engine:** `plan-loop`, `build`, `verify`, and `retro`, over a shared contract that owns the artifact, the status machine, the gates, and the adapter keys. A skill that contradicts the contract loses.
- **Chaining.** Each stage spawns the next, so an approved task runs to a merge-ready PR unattended. Bounded by one successor per skill, a two-round repair cap, a twelve-hop ceiling, and hard stops at both gates, at any contradiction of the approved plan, and at merge.
- **Ownership.** Whoever spawns an agent owns it and answers its questions. Every agent carries the root approved plan, so it checks itself against a real contract instead of inferring intent, and the user is reached only when something contradicts that contract.
- **Cross-repository work.** Reading any repository is free; writing to one must be named in the plan and approved at gate 2. Each companion repository gets a complete nested lifecycle of its own, bounded to one level of recursion with no repository entered twice in a lineage.
- **Plans left the product repository.** The working copy lives in a git-backed plan store — a plan is process, not deliverable — and the PR description became the published copy that survives after merge.
- **Verification is fresh by construction.** Verify is always a newly spawned agent that never saw the build, and re-verification after a repair covers every criterion, because a fix that breaks a neighbouring criterion is exactly what an unattended loop would otherwise carry to the PR.
- **Reports are plain English.** Point first, concrete nouns, failures before passes, and none of the system's own vocabulary.
- **Autonomous improvement, with a boundary.** Retro applies qualifying graduations itself and reports after the fact, but may never autonomously weaken the gates, the criteria freeze, the qualification bar, or the boundary itself. A self-improving system's most likely catastrophic improvement is optimizing away its own oversight.
